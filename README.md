# octane

octane is a coding agent for the terminal, written in Rust.

It runs end to end: eight tools, shell commands under an OS sandbox, a
streaming full-screen TUI, and a turn loop connected to real models.
Verified against Gemini 3.6 Flash over OpenRouter.

The design follows a survey of Claude Code, Codex CLI, opencode, Crush,
and Antigravity CLI. RESEARCH.md records what each does and which of
their decisions this project adopts.

## Requirements

A Nix installation with flakes enabled. The flake pins the Rust
toolchain, so there is no rustup and cargo is not on PATH outside the
dev shell.

## Building

    direnv allow          # or: nix develop
    cargo build --release
    cargo test --workspace

Without nix-direnv, `use flake` re-evaluates on every cd. To cache it:

    nix profile install nixpkgs#nix-direnv
    echo 'source $HOME/.nix-profile/share/nix-direnv/direnvrc' \
        >> ~/.config/direnv/direnvrc

## Running

    octane                  # interactive session
    octane doctor           # resolved config: model, sandbox, writable roots
    octane models           # configured providers and models
    octane connect          # set up a provider

`octane tool <name> <json>` runs one tool under the same policy and
containment a turn applies, which answers "is the sandbox on?" without
spending a token.

    octane tool read '{"path":"src/main.rs","limit":40}'
    octane tool bash '{"command":"cargo test","description":"runs tests"}'
    octane tool grep '{"pattern":"TODO","mode":"files","glob":"**/*.rs"}'

## Configuration

Configuration lives under `.octane/`, in two scopes: `~/.octane/` for
the user and `.octane/` for the project. The project wins field by
field, so a repository can pin its model without discarding the user's
permission rules.

    .octane/
    ├── settings.toml     model, permission mode, thinking, sandbox
    ├── providers/*.json  connections and their models
    └── agents/*.md       agent definitions

TOML for settings, JSON for providers. Settings are hand-edited and want
comments, which JSON cannot carry. Provider files are generated by
`octane connect` and mirror upstream JSON formats, where TOML tables
would make the nesting worse.

`/settings` is an editor. It lists what can change with each current
value, then that setting's possible values, and writes the choice.
Changes apply to the running session where possible; where they do not,
it says so.

Three rules govern it:

- Only settings with a knowable set of values are offered, so every
  choice is valid by construction. Free-text settings and `permissions`
  are absent. A broad grant should cost a considered file edit.
- Writes preserve the file. Serializing the struct back would delete
  every comment, and the starter template is entirely comments.
- An edit goes to the file that already sets the value, falling back to
  the project. Writing blind to the project would shadow a value set
  globally.

A setting that does nothing is never offered.

`octane settings` prints the resolved values and every settings file in
override order, marked present or absent, so a setting that is not
taking effect can be traced to the file that is missing.

## Providers

One JSON file per provider, declaring a connection and every model
reachable through it. Files are read from `~/.octane/providers/` and
`.octane/providers/`, with the filename as the provider key.

    octane connect                # what can be set up
    octane connect openrouter     # writes .octane/providers/openrouter.json
    octane --model corp/claude    # provider/model
    octane --model sonnet         # bare key, when unambiguous

`api` and `baseUrl` are per-model, not only per-provider. One gateway
commonly fronts `/chat/completions`, `/responses`, and `/messages` at
once, and Google's two flavours share a format while differing in URL
and auth.

    {
      "api": "openai-completion",
      "baseUrl": "https://gateway.corp/v1",
      "auth": { "type": "apiKey", "value": "${GATEWAY_TOKEN}" },
      "defaults": { "primary": "claude", "faster": "mini" },
      "models": {
        "gpt":    { "id": "gpt-5" },
        "o-next": { "id": "o-next", "api": "openai-responses" },
        "claude": { "id": "claude-sonnet-4-5", "api": "anthropic",
                    "baseUrl": "https://gateway.corp/anthropic/v1",
                    "auth": { "type": "apiKey",
                              "value": "${CORP_ANTHROPIC_TOKEN}",
                              "header": "x-api-key", "prefix": "" } },
        "gemini": { "id": "gemini-3-pro", "api": "google" }
      }
    }

Four wire formats cover essentially everything: `openai-completion`,
`openai-responses`, `anthropic`, `google`. Auth is typed rather than a
key string: `apiKey` with a configurable header and prefix, `none`,
`googleVertex`, `awsSigV4`, `tokenFile`.

`${VAR}` references keep a provider file safe to commit. A missing
variable is a load error naming the variable, and an unusable provider
is listed with its reason rather than silently dropped.

Worked examples are in `examples/providers/`.

Subscription sign-in for Claude Pro/Max and ChatGPT is not implemented,
deliberately. Anthropic sent legal demands to opencode over it in March
2026 and began blocking third-party OAuth in April. OpenAI documents the
flow only for its own clients, where the practical route is reusing
their client ID. API keys and `tokenFile` are offered instead.

## Agents

An agent is a system prompt, a tool subset, and a model, written as
markdown with YAML frontmatter:

    ---
    name: research
    description: Searches the codebase and reports findings with citations
    tools: [read, glob, grep, list]
    ---

    Report file paths and line numbers. Never speculate about code you
    have not read.

Six ship built in. `build` and `plan` are primary agents; `research`,
`test`, `code`, and `critic` are subagents, reachable only through
delegation.

The `task` tool takes an agent name and a prompt, runs that agent in its
own thread with its own tool set, and returns only the final report. The
separate context is the point: a search that reads thirty files should
cost the parent turn one paragraph. Primary agents are omitted from the
schema, since an agent that can delegate to itself will.

    /agents      what is defined, and from which scope
    /cs <query>  codebase search; fans out to research subagents
    /thinking    cycle reasoning: auto, off, low, medium, high
    /tools       what the model can call this turn, and what is withheld
    /stats       tokens, cache hit rate, and cost

When the context fills, octane prunes old tool output first, then
summarizes an old span of the conversation and continues. The cached
prefix and the recent turns are never summarized, and the span never
splits a tool call from its result. The summary runs on `faster-model`
when one is configured.

Not every endpoint honours `/thinking off`. Some refuse and reason
anyway; octane reports the refusal rather than ignoring it.

## The TUI

Full screen on the alternate screen: header at top, transcript in the
middle, composer and status pinned to the bottom.

That gives up the terminal's own scrollback, search, and selection.
`octane-tui::transcript` replaces it, with follow-tail as the property
that matters: new content keeps the view at the bottom until you scroll
up, then stops. Scrolling back down resumes following.

`@path` attaches a file, `!command` runs a shell command, `/` opens
commands. Both `@` and `/` complete as you type, matching by subsequence
rather than prefix, so `@octcli` finds
`crates/octane-cli/src/main.rs`.

Newlines have three bindings because one is not portable. Most terminals
send a bare CR for shift+enter unless the keyboard enhancement protocol
is negotiated, which octane requests at startup. `alt+enter` works
essentially everywhere, and a trailing backslash needs no terminal
support.

The transcript renders markdown, with one divergence from CommonMark:
`_` never opens emphasis. By the spec `a_variable_name` is unambiguous,
but a transcript full of identifiers gets mangled as soon as a line
holds two underscores in the wrong places.

Every module except `app` is pure, so rendering, key routing, and
completion are testable by calling a function.

Glyphs are chosen for width safety. A character that renders
double-width in one terminal and single in another destroys every box
and aligned column, and the breakage is invisible until someone reports
it from a terminal you do not have. Everything comes from ranges that
are unambiguously narrow. U+26A1 and U+2714 look like plain symbols but
default to emoji presentation and take two cells; U+2713 does not. An
ASCII set covers terminals without dependable Unicode, and it reaches
the transcript and status line, not only the banner.

## Layout

One responsibility per crate, with strictly one-way dependencies.

| Crate | Owns |
|---|---|
| `octane-protocol` | Thread, Turn, Item, Message, Part, Event |
| `octane-provider` | `LanguageModel`, stream events, transforms, pricing |
| `octane-tools` | `Tool`, the registry, the built-in tools |
| `octane-permission` | `action(target)` policy; allow, ask, deny; modes |
| `octane-sandbox` | Seatbelt, Landlock, AppContainer containment |
| `octane-context` | token budget, pruning, compaction thresholds |
| `octane-memory` | `OCTANE.md` and `AGENTS.md` layering, `@imports` |
| `octane-skills` | skill discovery, progressive disclosure |
| `octane-commands` | slash command discovery and template expansion |
| `octane-config` | `.octane/` discovery, settings, agent definitions |
| `octane-mcp` | MCP JSON-RPC lifecycle, stdio transport, adapter |
| `octane-core` | the turn loop, agents, prompt assembly, stop conditions |
| `octane-tui` | composer, keymap, rendering, approvals |
| `octane-cli` | argument parsing, config resolution |

`octane-core` coordinates and holds no domain logic. Every collaborator
is a trait, which is why the loop is testable without a model, a shell,
or a network.

## Policy and containment

These are separate layers and are easy to conflate.

Policy (`octane-permission`) asks whether an action should be allowed,
and runs before a command does. Containment (`octane-sandbox`) asks what
a process can reach if it does something other than what it said, and is
enforced by the kernel.

Both are needed. Policy alone trusts that `make test` does what its name
suggests. Containment alone blocks silently and produces failures the
model cannot diagnose.

## Notes

Decisions that are not obvious from the code:

- Precedence is deny, then ask, then allow. A broad `ask(command(*))`
  beats a narrow `allow(command(git))`. One exception: an interactive
  grant made this session outranks a configured `ask`, or "remember my
  answer" is impossible.
- `.git/` and `.octane/` are read-only inside writable roots. Otherwise
  a project-write grant reaches `.git/hooks/pre-commit`, which is
  arbitrary code on the next commit, and lets the agent rewrite its own
  policy.
- Sandbox paths are passed as `-D` parameters and never interpolated
  into the Seatbelt profile. A directory named `") (allow default) ("`
  would otherwise rewrite the policy. There is a test for it.
- An unsupported platform is a sandbox error, not a pass.
- Tool schemas live in a `BTreeMap`. They sit in the cached prompt
  prefix, so hash-map iteration order would reorder them between turns
  and void every cache hit. Codex shipped this bug with MCP tools.
- The prompt is append-only. Configuration that changes mid-session is
  appended as a developer message, never edited into what was sent.
- The system prompt is assembled once per session, most-static first:
  instructions, sandbox description, project memory, environment.
  Rebuilding it per turn can change the prefix mid-session.
- The model is told what the sandbox permits. A model that does not know
  it is confined reads a denial as a broken command and tries to fix
  working code.
- A denial ends the turn. Reporting a refusal invites the model to find
  another route to the same action.
- A broken harness is not reported to the model. On a platform with no
  sandbox backend that is every `bash` call, which would burn the step
  budget rediscovering that the tool is unavailable.
- Plan mode omits mutating tools from the prompt rather than only
  refusing them. A denial ends the turn, so a visible `write` is a turn
  that can be lost.
- The permission mode and the status line are the same value. They were
  not always: shift+tab moved the label while the engine kept evaluating
  the mode it started with.
- The model decides when the task is done. The step cap, loop detector,
  and context thresholds are safety rails, not completion criteria.
- Loop detection hashes tool, input, and output together. A repeated
  call whose output changed is progress, such as polling a build.
- A subagent returns its report, not its transcript.
- `.gitignore` is honoured outside a git repository. `ignore` defaults
  the other way to match ripgrep's CLI, but an agent is pointed at
  extracted archives and vendored subtrees that have a `.gitignore` and
  no `.git`.
- `glob` sorts by mtime, `list` sorts alphabetically. Recency is the
  cheapest relevance signal when hunting for a file, but a tree whose
  branches move between calls is hard to reason about.
- An approval prompt accepts instructions, not only yes or no. The
  common case is not "no", it is "no, do it this other way".
- There is no "always allow" key. A grant that broad should be a
  deliberate config edit.
- Esc interrupts and does not exit. `ctrl+d` exits only on an empty
  composer.

## Not yet wired

Written and tested, but not reachable from the binary:

- MCP. `octane-mcp` speaks the protocol and the permission engine models
  MCP tools, but nothing spawns a server and the crate is not in the
  binary's dependency tree.
- Skills reaching the model. `/name` prints a skill body into the
  transcript, and the tier-1 manifest is not in the system prompt.
- File-based slash commands. `octane-commands` discovers and expands
  `.octane/commands/*.md`; the binary's command list is hardcoded.
- `faster-model`. Used for compaction; nothing else asks for the faster
  role yet.

## Testing

    cargo test --workspace              # 683 tests
    cargo clippy --workspace --all-targets
    python3 scripts/tui-smoke.py        # drives the TUI through a pty

Tests are named for the property they protect, such as
`a_path_with_shell_metacharacters_cannot_reach_the_profile` and
`changing_output_is_progress_not_a_loop`.

`crates/octane-tools/tests/sandbox_execution.rs` asserts the security
claim against the real kernel sandbox: a write outside the writable
roots, to `.git/hooks/`, or to the network does not land.
`danger_full_access_is_genuinely_unconfined` is the negative control,
which is what makes the other results evidence rather than coincidence.
macOS only, since Seatbelt is the only backend implemented.
